# 부산브리핑 — Phase 분리 계획

> 한 번에 다 만들면 복잡해져서 품질이 떨어집니다.
> Phase별로 나눠서 각각 "진짜 동작하는 제품"을 만듭니다.

---

## Phase 1: MVP — 단지 한 장 브리핑 + PDF (2주)

### 목표
**손님 앞에서 단지명 검색 → 한 페이지 브리핑 → PDF 다운로드까지 끊김 없이.**
이 Phase가 끝나면 당장 내일 상담부터 사용 가능.

### 기능
- [ ] 공용 비밀번호 1개 로그인 (Streamlit secrets)
- [ ] 단지명 자동완성 검색 (apt_complex 4,278건)
- [ ] 단지 브리핑 페이지 한 장
  - [ ] 단지 정보 카드 (건축년도/평형 범위/도로명/총 거래수)
  - [ ] 5년 시세 추이 차트 (월별 평균가, 평형 필터)
  - [ ] 5년 전월세 추이 차트 (전세 vs 월세 분리)
  - [ ] 같은 구 내 거래량·평균가 랭킹 (apt_complex.trade_count)
  - [ ] 주변 인프라 요약 카드 (자치구 학교/병원/약국/학원 수)
  - [ ] 자치구 인구 추이 차트 (population_gu 60개월)
- [ ] PDF 다운로드 (WeasyPrint, A4 1~2장)
- [ ] 최근 본 단지 5개 사이드바 표시

### 데이터
- 읽기만: `apt_trade`, `apt_rent`, `apt_complex`, `schools`, `medical`, `pharmacy`, `academies`, `population_gu`, `gu_codes_realty`
- 새로 생성: **없음** (Phase 1은 사용자 데이터 저장 0)

### 인증
- Streamlit secrets에 `APP_PASSWORD` 저장 → 첫 진입 시 비밀번호 입력 → 세션 유지

### "진짜 제품" 체크리스트
- [ ] 실제 bptc_realestate.db에 연결 (목업 데이터 X)
- [ ] 실제 비밀번호 인증 (코드 하드코딩 X, secrets.toml 사용)
- [ ] 로컬 PC에서 `streamlit run app.py` 한 번으로 실행
- [ ] 손님과 화면 공유 시 1280×800 해상도에서 깨지지 않음
- [ ] PDF가 A4 인쇄 시 잘리지 않음

## Phase 2: 확장 — 손님 관리 + 비교 + 매칭 (3주)

### 전제 조건
- Phase 1이 사무실 PC에서 안정적으로 돌아감
- 중개인이 Phase 1을 1주 이상 실사용해서 UX 피드백 수집됨

### 목표
**상담 한 번이 일회성으로 끝나지 않고 손님 DB로 누적.**
손님 조건만 입력하면 후보 단지가 자동으로 떠야 함.

### 기능
- [ ] 새 DB 파일 `briefing_app.db` 생성 + `ATTACH DATABASE`
- [ ] 손님 등록·조회·수정·삭제 (customer)
- [ ] 손님별 상담 메모 + 마지막 연락일 관리
- [ ] **단지 2개 나란히 비교 화면**
  - [ ] 가격·평형·건축년도·거래량 좌우 대조표
  - [ ] 두 단지 시세 추이 한 차트에 오버레이
  - [ ] 학군·인프라 점수 카드 비교
- [ ] **매칭 엔진**
  - [ ] 손님 조건 입력 폼 (구/예산/평형/매매 vs 전세/학군 우선)
  - [ ] 점수 산정 룰 (예산 적합 30점, 평형 적합 20점, 학군 강세 20점, 거래 활발 15점, 신축 15점)
  - [ ] 후보 단지 점수 순 리스트 + 이유 표시
  - [ ] match_result 자동 저장
- [ ] 브리핑 이력 (briefing) — 손님 페이지에서 "이전에 보여준 브리핑" 재다운로드

### 추가 데이터
- 새 테이블: `customer`, `briefing`, `match_result`
- 인덱스: `idx_customer_gu`, `idx_briefing_customer`, `idx_match_run`

### 통합 테스트
- [ ] Phase 1 단지 브리핑이 여전히 정상 동작
- [ ] 손님 100명 등록 후 매칭 결과 2초 이내
- [ ] 브리핑 생성 시 customer_id가 옵션 — 손님 없이 단발성 브리핑도 여전히 가능

### Phase 2 시작 프롬프트
```
Phase 1이 안정화된 상태에서 Phase 2를 추가해주세요.
@PRD/ 폴더 전체 참고.

Phase 2 범위:
- briefing_app.db 새로 만들고 ATTACH로 결합
- customer / briefing / match_result 3개 테이블
- 손님 CRUD 페이지
- 단지 2개 비교 페이지
- 조건 입력 → 매칭 점수 알고리즘

지켜야 할 것:
- bptc_realestate.db는 절대 수정 금지 (마이그레이션도 금지)
- Phase 1 화면/URL/기능 깨뜨리지 않기
- 점수 가중치는 별도 config 파일로 분리 (튜닝 가능하게)
```

## Phase 3: 고도화 — 일일 리포트 + 공유 URL (2주)

### 전제 조건
- Phase 1 + 2가 안정적으로 운영 중
- 손님 데이터가 누적되어 매칭 정확도 검증된 상태

### 목표
**중개인이 잠든 사이 시장 변화가 정리되어 있고, 손님이 폰에서 다시 본다.**

### 기능
- [ ] 영업 자치구 설정 (1~3개 구)
- [ ] 일일 리포트 자동 생성 (cron/Windows 작업 스케줄러 06:00)
  - [ ] 어제 거래 TOP 5
  - [ ] 어제 최고가
  - [ ] 이상거래 탐지 (평균 대비 ±20% 룰)
- [ ] 일일 리포트 페이지 + PDF
- [ ] 브리핑 공유 URL 생성 (단축 토큰, 만료 7일)
- [ ] 손님이 URL 열면 viewed_at 자동 기록
- [ ] 테마 대시보드 (선택)
  - [ ] 학군 강세 자치구 TOP (academies.ipsi_count 기반)
  - [ ] 의료 인프라 자치구 랭킹
  - [ ] 교통 접근성 (gu_centers 기반 거리)

### 주의사항
- 공유 URL은 **외부 노출** — 인증 없이 누구나 토큰만 알면 접근. 민감 메모(broker_memo)는 절대 렌더링 금지.
- 일일 리포트 자동 실행은 OS 작업 스케줄러에 의존. 실패 시 알림 채널 없음 — 수동 점검 필요.
- 이상거래 탐지 룰은 통계적 근거가 약함 (단순 평균 대비). "참고용"으로만 표기.

### Phase 3 시작 프롬프트
```
Phase 1+2 위에 Phase 3를 추가해주세요.
@PRD/ 폴더 전체 참고.

Phase 3 범위:
- daily_report 테이블 + 자동 생성 스크립트
- 영업구 설정 페이지
- briefing.share_url 토큰 + 외부 공개 페이지
- 손님이 링크 열면 viewed_at 기록

지켜야 할 것:
- 공유 페이지에 broker_memo 절대 노출 금지
- 토큰 만료 7일 강제
- 일일 리포트 스크립트는 단독 실행 가능 (Streamlit 의존 X)
- 이상거래 판정에 "참고용" 워터마크 필수
```

## Phase 4: 데이터 자동 갱신 (보류 — 나중에 결정)

### 전제 조건
- Phase 1~3까지 실사용 1개월 이상
- 어떤 테이블이 자주 보이는지 우선순위 검증됨

### 그동안의 임시 운영
- 새 DB가 필요해지면 `02_데이터베이스/bptc_realestate.db` 파일만 수동 교체
- 앱 코드 변경 없음. 첫 2~3개월은 이걸로 충분

### 목표 (확정 시)
**매월 1회, 본인 손 없이 최신 데이터로 갱신.**

### 후보 기능 (결정 보류)
- [ ] 국토부 실거래가 API 호출 스크립트 (apt_trade, apt_rent)
  - 16개 자치구 × 변경분 월 호출
  - apt_complex 자동 재집계
- [ ] 부산시 인구 통계 갱신 (population_gu)
- [ ] 학교·의료·약국·학원 갱신 (분기/연 단위, 자주 안 바뀜)
- [ ] 갱신 트리거 — 셋 중 택 1
  - 앱 시작 시 "마지막 갱신 N일 전, 지금 갱신할까요?" 모달
  - Windows 작업 스케줄러 매월 1일 새벽
  - 둘 다 (수동 + 백그라운드)
- [ ] 갱신 실패 시 롤백 (이전 DB 백업)
- [ ] 갱신 로그 화면 (언제 몇 건 받았는지)

### 결정해야 할 것 (Phase 4 진입 시)
- [ ] API 키 발급 주체 (본인 직접 vs 사전 발급 동봉)
- [ ] 갱신 트리거 방식
- [ ] DB 백업 보관 정책 (직전 3개월? 1년?)
- [ ] 학교·인구 등 비-실거래 데이터 포함 여부

### 왜 지금 안 하나
- DB가 이미 2026-05까지 채워져 있어 당장 갱신 불필요
- Phase 1~3 미완 상태에서 자동화 = 동작 안 하는 걸 자동화하는 격
- 실사용해봐야 "어떤 데이터가 자주 stale 하다고 느끼는지" 판단 가능
- API 키 발급은 1~2일이라 Phase 1~3 개발 중 병행 가능

## Phase 로드맵 요약

| Phase | 핵심 기능 | 기간 | 상태 |
|-------|----------|------|------|
| Phase 1 (MVP) | 단지 브리핑 + PDF + 비밀번호 로그인 | 2주 | 시작 전 |
